# VoxFlame 研究—发现—实验—落地 Harness

> 入口契约：每轮任务先从根 [`AGENTS.md`](../AGENTS.md) 分流；本文件负责研究对象的生命周期和证据门，机器规则以 [`HARNESS_RULES.yaml`](HARNESS_RULES.yaml) 为准，脚本只执行规则，不另立阈值。

## 目标

把“发现新信息”变成可复核、可实验、可落地、可回退的单一闭环。研究不以文章数量或模型分数为完成标准，而以是否改善真实沟通成功率、训练反馈质量或部署可靠性为最终标准。

## 唯一事实源与对象关系

一个研究机会只有一个 `research_id`，生命周期中的所有材料都用它关联：

```text
Research Opportunity (RO)
  ├─ Discovery / Source claims        发现与来源主张
  ├─ Evidence Review                  证据核验与限制
  ├─ Experiment / Prototype           实验、原型与固定对照
  ├─ Scholarly / IP Outcome           论文、专利、软件著作权、数据集与开源成果
  ├─ Product Scenario Pilot           产品场景试点
  └─ Optimization Loop               指标复盘、改进、回退或淘汰
```

机器可读索引是 [`research/PIPELINE.yaml`](PIPELINE.yaml)；正文、实验记录、专利/论文材料和场景报告都必须在索引里登记，不能只靠目录约定。

每个 `research_id` 还必须挂一份 `review_report`。它是发布/申请/扩展前的初步审查与改进建议记录；报告缺失时，流程只能停在内部研究。

## 生命周期状态

状态是研究对象的事实状态，不等同于应用回流中的 `adopt / validate / hold / reject` 决策。任何状态变更都必须在 Pipeline、证据包、反馈和应用回流之间保持同一 `research_id`。

| 阶段 | 进入条件 | 必须产物 | 退出门槛 |
| --- | --- | --- | --- |
| `discovered` | 发现一个与五大主题相关的机会 | 一句话问题、来源 URL、发现时间、为什么与 VoxFlame 相关 | 来源身份和范围可核验；否则停在 `watch` |
| `evidence_review` | 至少一个锚点来源或可追溯原始材料 | 证据表、限制、反证/冲突、适用人群/设备/场景 | 证据等级和待验证假设清楚 |
| `experiment_ready` | 假设可被证伪 | 固定数据、基线、指标、停止条件、owner、预算 | 可复跑命令/配置和回退路径存在 |
| `experimenting` | 实验已开始 | 运行记录、版本/commit、原始产物、日志 | 结果可复核，不能只报最好一次 |
| `outcome_review` | 实验完成或有足够负结果 | 结果、统计/误差、不能外推项、论文/专利/IP 评估 | 明确 `reject / hold / validate / adopt` |
| `authority_review` | 准备对外发布或扩大 idea 范围 | 权威来源矩阵、独立复核、反证和适用边界 | 对应发布/扩展闸门明确 `pass`，否则不得发布或扩展 |
| `scholarly_ip` | 有可公开或可保护的新颖贡献 | 论文草稿、数据卡、专利披露或开源说明；作者/发明人和权属 | 合规、署名、公开时机和证据链审查完成 |
| `scenario_pilot` | 通过结果门槛且有现役 owner | 场景目标、用户授权、feature flag、试点协议、监控 | 真实任务指标达到门槛，安全与回退可用 |
| `adopted` | 产品/工程/用户证据均满足门槛 | PRD/任务/代码/文档同步，应用回流登记为 `adopt` | 持续监控；出现回退信号自动转 `improving` 或 `rolled_back` |
| `improving` | 试点或生产发现问题/机会 | 变更假设、回归对照、版本和影响分析 | 达标回到 `scenario_pilot`/`adopted`，否则 `rejected` |
| `hold` / `rejected` | 证据不足、风险不可接受或实验否定 | 具体阻塞/否定证据和再评估触发条件 | 禁止换名后重新进入同一条线 |

### 阶段不是线性发布通道

- `scholarly_ip` 不是产品采用的前置条件；没有论文/专利也可以做产品试点。
- `scenario_pilot` 不是把实验结果直接上线；必须有用户授权、隔离开关和回退。
- 任何论文/专利/公开数据/开源发布，或扩大到新用户、新病因、新语言、新设备、新场景、新承诺前，必须先进入 `authority_review`。
- `authority_review` 未通过时，只能内部研究、封闭实验或明确标注的候选，不得对外发布、扩大范围或写入默认产品承诺。
- 论文、专利、开源成果必须从同一个实验事实源生成，不能为发表重写结果。
- 任何阶段都允许记录负结果；负结果是优化和淘汰的重要输入。

## 证据与门禁

### 四类证据必须分开

1. **机制证据**：为什么可能有效，适用条件和反例是什么。
2. **工程证据**：延迟、可靠性、资源、权限、可观测性和部署成本。
3. **产品证据**：用户是否理解、愿意控制、能恢复、愿意继续使用。
4. **场景证据**：在医院、工作、陌生人求助、家庭、训练等真实任务中是否减少失败。

一个证据不能代替另一个证据。尤其是离线 CER、benchmark 或专家观点，不能单独证明真实沟通收益。

### 产品与硬件规划的四种来源状态

涉及产品路线、硬件规格、辅助器具、医疗/健康相邻能力和采购时，在四类证据之外还必须标注“这条需求从哪里来”：

| 状态 | 含义 | 能做什么 | 不能做什么 |
| --- | --- | --- | --- |
| `V` | 目标用户/沟通伙伴在真实或高保真任务中验证 | 进入产品 Gate 与验收 | 跨人群、语言、场景外推 |
| `E` | 官方标准/监管指南/专业学会/原厂资料/论文 | 建立机制、约束、风险和候选参数 | 证明 VoxFlame 整机效果 |
| `Q` | 至少两家供应商或实验室同口径书面答复/报价 | 决定成本、工期、供货和认证路径 | 证明用户价值 |
| `H` | 团队、供应商或 AI 提出的待验证假设 | 形成访谈、实验、原型和停止条件 | 对外承诺、冻结 BOM 或批准量产 |

供应商 PRD、竞品功能、创始人直觉和 AI 草案可以是重要输入，但默认都是 `H`，直到被相应证据升级。精确数字不会自动提高证据等级。

### 产品文档的受众分层

内部事实源、原供应商反馈稿和中性供应商征询稿必须可追溯但不能混为一份：

| 版本 | 必须保留 | 必须移除或隔离 |
| --- | --- | --- |
| 内部决策 | V/E/Q/H、支付方、完全落地成本、预算/毛利假设、异议、停止条件、Gate | 不删负面证据，不把假设包装成对外承诺 |
| 原供应商反馈 | 对方熟悉的章节骨架、表格密度、术语入口和后续回复要求；仅在任务明确需要时加入章节映射与纠偏理由 | 不泄露内部谈判底牌；用户要求最终产品方案时，不保留对照、研究过程或角色阅读说明 |
| 中性供应商征询 | 自有产品定义、全系统功能、路线状态、当前优先范围、强制/目标/候选/待确认、验证、交付、偏离和同口径报价 | 原稿/修订/对照痕迹、内部预算上限、毛利、签批意见、无授权竞争情报 |

对外稿中的完整路线只用于说明产品组合与复用边界；编号或长期方向不得被解释为已经批准的订单、排期、数量或预算。经营、产品、软硬件、供应链、质量、法规和售后视角应融合成一套连续的需求、取舍、验收与退出条件，不通过“某角色看某一章”组织正文。发布前检查品牌词、全文禁词、媒体资源、版本元数据和 PDF 版式，并保留可重复生成脚本。

任何具体参数都要进入逐项台账并标记 `原厂事实 / 候选配置 / 采购或测试目标 / 未知`。原厂数字必须保留料号、版本、工作条件和不能外推的边界；整机目标必须保留样机阶段、固定工作负载、测试方法和冻结 owner。没有一手材料、书面报价或样机数据时，不允许用同类产品、搜索摘要或 AI 推理补成已实现参数。

### 下载材料的内容真实性门禁

保存外部原文时，最低记录 `publisher / title / source_url / accessed_at / HTTP result / actual MIME or file type / page count or schema / SHA-256 / intended use / limitation`。

- 搜索结果只用于发现，必须实际打开原文。
- `.pdf` URL 返回 HTML 网页壳、登录页或无关文件时，标记失败并移除错误副本。
- 官方链接不可达时记录具体失败和最接近的权威替代来源；不得暗示已读取不可访问内容。
- 监管材料只能支持其管辖范围内的方法/要求；作为工程参照时必须显式说明“不等于分类、认证或有效性”。
- 竞品/原厂材料只能支持公开功能或器件能力；成本、整机表现和目标用户效果仍需 `Q` 与 `V`。

### 通用最小门槛

- 有固定 baseline、数据/人群范围、版本/commit、随机种子或运行参数。
- 有主要指标、保护指标（延迟/可打断/错误恢复/隐私）和停止条件。
- 有反例、失败样本和不能外推的范围。
- 有现役 owner、最小切片、feature flag 和回退方式。
- 涉及语音：必须补 ASR 不确定性、停顿/打断、噪声、设备和跨用户隔离。
- 涉及健康：必须补专家复核、目标人群验证、隐私、合规和非诊断边界。
- 涉及硬件/采购：内部事实源必须补支付方、完全落地成本、COTS/ODM baseline、两家同口径 RFI/RFQ、生命周期/维修/退市、Gate 预算和停止条件；BOM 单价不能代替商业可行性。对外供应商版保留统一报价字段和停止/验收边界，但不得披露未批准的预算上限或毛利底牌。

### 普通话录音语料的可复现证据门

普通话录音区的根本目标是语言学覆盖和真实采集可用性，不是把主观审稿流程包装成“科学门槛”。候选题面分为两层：

1. `recording_ready`：允许进入录音区。只执行可重复的机器/工程规则：
   - 来源可追溯，保留来源、版本/快照、许可线索和目标读音证据；
   - 目标音节—声调由整词读音或整句拼音重新计算命中，不得只靠单字猜读；
   - 使用简体中文和现代普通话字符；清理无法解析的字符、繁体泄漏、商业学习包/课程包/培训包/资料包、明显敏感或高风险内容；
   - 句长、标点、可读字符数和重复结构符合录音工程约束；同一目标至少保留词项/短句的可追踪承载关系；
   - 与现役题库去重，并记录目标、任务分区、来源和筛选原因。
2. `training_import_ready`：不得由录音区可见性自动推导。必须在录音后依据有效音频、非空 `target`、授权和质量状态另行判定；模型训练导入还要通过数据集版本和 speaker-disjoint 评测门。

“自然度”“产品价值”“用户负担”可以作为后续研究变量，但不能作为没有量表、样本、评定者一致性和可复现判定函数的上线硬门。缺少合适中文句时，应回到有来源的普通话教材/测试材料/词典或许可语料重新找句；找不到就标记缺口，不用主观编句伪装完整。

录音质量只做分层与复录提示，不自动删除构音障碍样本。最低状态为：`valid`、`suspected_misread`、`suspected_omission`、`long_silence`、`unusable_audio`。ASR 只能产生疑似错读/漏读提示；覆盖统计的采集资格按“有效音频 + 非空 target”计算，人工 `spoken_text` 仅为可选质量诊断，不是录音前置条件。

双人复核不是本项目的录音、覆盖或训练导入流程。不得新增双人复核页面、脚本、统计字段或审批门；不得把两名审核者、人工 `spoken_text` 或音频—文本一致性确认设为录音可见、覆盖计数或训练导入的前置条件。若需要定位错读、漏读、空白过长或不可用音频，只能使用受保护的单人可选质量诊断旁路，并保留原始音频、manifest 和 `target`。任何复核流程变更都必须先证明它改善真实沟通成功率、质量诊断或部署可靠性，否则保持移除状态。

#### 标准的科学/工程依据

普通话覆盖标准、题面标准和录音质量标准必须分层记录：

- 语言学标准的分母来自版本化普通话音节—声调参考集、规范字读音和整词/整句拼音证据；目标集合、来源快照和生成版本必须可重跑。
- 题面长度、字符、标点、重复和商业污染是录音工程/数据工程约束，不是“中文自然度”的替代指标。词项与短句使用不同长度规则；阈值必须带单位、版本、适用范围和回归测试。
- 采集资格来自可验证摄取契约：稳定 `recording_id`、非空 `target`、正的音频时长/文件大小、授权 scope 和上传状态。人工转写与 ASR 置信度不改变这条事实口径。
- 错读、漏读、空白过长和不可用音频是录音后的质量诊断状态；自动规则只分层和提示复录，不删除原始构音障碍样本。阈值要用标注样本、误报/漏报和 speaker-disjoint 评测复核。

没有量表、样本、评定者一致性和可复现函数的“自然度”“产品价值”“用户负担”只能登记为待验证假设，不能成为录音前置硬门。规则变更必须留下 `rejection_code`、版本、反例和回退路径。

### 成果与产品的强证据门禁

论文、专利和产品不是“实验完成后自动升级”的三种包装，而是三种不同的审查对象。每一种都必须有独立的证据包：

| 结果 | 强制证据包 | 不满足时 |
| --- | --- | --- |
| 学术成果 | 原始数据/代码或可复现实验、固定版本、统计与不确定性、相关工作、伦理/数据许可、独立同行或导师复核；中文投稿还要做 CNKI/万方/NSTL 与出版伦理核验 | 只能是内部研究稿，不宣称已验证成果 |
| 专利 | 技术披露、发明人/权属、申请前新颖性/创造性/实用性检索、公开时机和法务/专利代理人复核 | 只能是 invention candidate，不对外披露核心方案 |
| 软件著作权 | 中国版权保护中心/国家版权局办事材料核验、权属链、源程序/文档版本固化、第三方许可和独立材料复核 | 只能是登记材料候选，不宣称已登记或获得技术效果保护 |
| 产品场景 | 独立于开发者的真实用户/沟通伙伴验证、现役 baseline 对照、任务成功率、保护指标、隐私/安全检查、灰度与回退演练 | 只能做隔离试点，不进入默认产品能力 |

“独立”至少意味着审查人不是唯一实验执行者；高风险健康能力还需要专业人员和目标人群复核。单篇论文、专家社媒、厂商案例、内部 demo 或满意度反馈都不能单独通过这些门禁。

### 发布与 Idea 扩展的权威闸门

`authority_gate` 是发布前和扩展前的硬阻断。每个闸门必须回答：主张是什么、谁能证明、证明了什么、哪里不成立、谁复核过、什么会阻止发布/扩展。

最低通过条件：`authority_sources >= 2`（至少一个 `primary` 或 `professional`，且来源彼此独立）、`independent_review.result = pass`、反证已记录、边界已记录、目标范围与证据范围一致。否则状态必须是 `hold` 或 `internal_only`。

## 实验到成果到产品的分流

```text
证据审阅
  ├─ 证据不足 -> hold / 继续发现
  ├─ 结果否定 -> rejected + 负结果归档
  ├─ 机制成立但产品未知 -> experiment_ready / scenario_pilot
  ├─ 准备发布或扩展 -> authority_review（不通过则 hold/internal_only）
  ├─ 有新颖、可复现贡献 -> authority_review -> scholarly_ip（论文/专利/软著/开源）
  └─ 真实任务改善 -> adopted -> 持续优化
```

论文/专利/产品三条线共享：数据版本、代码 commit、实验结果、限制和作者/发明人权属；各自增加不同材料：

- 论文：研究问题、相关工作、方法、统计、可复现材料、伦理声明。
- 专利：申请前新颖性/创造性/实用性检索、技术方案、权属、公开时机和保密边界。
- 产品：用户任务、交互/权限、owner、SLO、灰度、反馈和回退。

## 优化闭环

每次试点或发布后，必须把结果回写同一 `research_id`：

```text
真实反馈/监控
  -> 按失败类型归因（模型 / 上下文 / 工具 / UX / 设备 / 场景）
  -> 新假设与变更范围
  -> 固定 baseline 回归
  -> 小流量试点
  -> 达标采用，或记录负结果并淘汰
```

禁止直接把用户反馈改成 prompt、模型参数或产品功能；先写成可证伪假设，再进入实验。

## 自动触发与人工确认边界

触发器只负责把可观察信号变成 `FEEDBACK_REGISTRY.yaml` 的待处理输入，不自动宣称结论、扩大用户承诺或执行高风险变更。触发来源包括：

- 用户明确报告故障，或同类故障在 7 天内重复出现；
- API/RTC 的 P95/P99、5xx、429、超时、丢包、Job 拒绝率超过 RO 中的保护阈值；
- 根盘达到 50%（告警）、60%（安全清理）或 85%（人工升级）；
- Agent/ASR/TTS 资源达到内存、连接数、文件描述符或并发信号量上限；
- 修复已部署但缺少真实设备/用户场景证据；新设备、语言、人群或场景准备扩大范围。

触发后的最小动作是：生成或更新反馈 ID，关联唯一 `research_id`，记录指标快照和证据路径，给出可证伪假设、owner、验证指标和停止条件。低风险工程指标可以自动进入 `new` 或 `triaged`；以下事项必须人工确认后才能继续：真实设备/目标用户试点、生产流量扩大、扩容采购、数据库或对象存储删除、医疗/健康主张、对外发布和默认能力升级。

闭环完成定义：反馈有证据 → RO 有 baseline/停止条件 → 实验或最小实现可回退 → 结果写入 outcome review → 场景/保护指标验证 → 应用回流登记 → 设定下一次复核日期。没有验证结果的“已处理”只能保持 `validating` 或 `improving`，不能标记 `resolved`/`adopted`。

推荐命令：

```bash
python3 scripts/research/check-research-triggers.py metrics.json
python3 scripts/research/create-feedback-entry.py --research-id RO-014 --source telemetry --scenario "RTC 阶梯压测" --observation "ASR P95 超过阈值" --severity high --failure-type network --evidence-ref artifacts/run.json --hypothesis "外部 provider 并发达到上限" --owner "livekit_agent" --action "停止加压并补信号量" --validation "ASR P95 <2s 且 429=0"
python3 scripts/research/validate-research-loop.py
```

触发器不读取 secrets、不删除数据、不直接修改运行时配置；所有副作用操作仍沿现有部署和审批流程执行。

触发器的阈值、允许动作、禁止动作和人工确认清单不得在报告或业务脚本中重复定义；修改阈值时先改 `HARNESS_RULES.yaml`，再运行研究系统检查和触发器回归。

反馈不是附录，而是优化输入。每次反馈必须有来源、场景、严重度、影响指标、归因置信度、责任 owner、动作、验证结果和关闭条件；没有动作或验证的“收集意见”不算完成闭环。

## 最小记录要求

### 跨端注册与商业用途授权规则

Web 与 App 是同一产品能力的两个 UI 适配面。注册字段、授权用途、授权版本、撤回/删除/导出语义和训练数据边界必须共享同一事实源；允许平台使用不同布局、控件和交互节奏，但不得一端缺少另一端已有的注册资料或授权项。

涉及语音、转写、方言、病种等敏感信息时，注册或首次进入对应功能必须分项记录：隐私处理、敏感信息处理、数据采集、商业用途。商业用途须明确写出模型训练、评测、产品改进和服务运营范围，并说明不出售身份信息、不作违法用途、不扩大到未披露目的。用户必须可分别拒绝、撤回、申请删除和导出；已匿名化、聚合或进入模型版本的数据要提前说明可能无法逐条逆向删除。

旧账号没有当前授权版本时，只能在需要对应数据用途的功能入口重新确认，不得静默补勾选；未同意商业用途不得把新录音导入商业训练链路。

每个 `research_id` 至少登记：

- 问题、主题、owner、目标场景和用户价值假设
- 来源与证据等级、发布日期/版本、访问时间和限制
- baseline、实验配置、数据/人群、指标、停止条件和结果
- 论文/专利/开源成果状态、贡献人和权属风险
- 产品 owner、contract、feature flag、试点范围、用户授权和回退
- 当前状态、下一步、最后复核时间和重新评估触发条件
- 反馈条目、失败样本和由反馈触发的实验/回退记录

## 工程闭环与语音评测

研究中的工程变更遵循 **发现需求 → 实现 → 优化 → 测试 → 迭代**，不替代上面的 RO 生命周期；测试失败回到实现/优化，缺测不升级采用。语音按 [官方工程指标协议](voice-agent/VOICE_AGENT_BENCHMARK_PROTOCOL.md)，沿同一证据包的 `benchmark_runs` 引用脱敏 JSON；研究检查执行离线结构/口径守卫与回归测试。未登记外部文件或仅报告退出码 0 不证明验收通过。自动触发器明确返回缺测列表，并读取 rules 的 TTS/丢包保护阈值；benchmark 报告不直接当生产遥测。目标用户/设备与外部服务调用仍需确认。
